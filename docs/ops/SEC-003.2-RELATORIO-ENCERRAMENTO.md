### 6. CONSULTAS DE MONITORAMENTO OPERACIONAL

Para o acompanhamento contínuo dos agendamentos em produção, utilizar as consultas padronizadas abaixo:

```sql
-- 1. Status da última execução de cada agendamento no pg_cron
SELECT 
  j.jobid,
  j.jobname,
  d.runid,
  d.status,
  d.return_message,
  d.start_time,
  d.end_time,
  ROUND(EXTRACT(EPOCH FROM (d.end_time - d.start_time))::numeric, 3) AS duracao_segundos
FROM cron.job j
LEFT JOIN LATERAL (
  SELECT * FROM cron.job_run_details rd 
  WHERE rd.jobid = j.jobid 
  ORDER BY rd.start_time DESC 
  LIMIT 1
) d ON true
ORDER BY j.jobid;

-- 2. Histórico de chamadas e despachos do Dispatcher
SELECT 
  id,
  job_name,
  function_name,
  status,
  message,
  created_at
FROM public.cron_execution_logs
ORDER BY created_at DESC
LIMIT 15;

-- 3. Respostas da extensão pg_net (notar que rotinas longas >5s registram timeout cliente mas continuam executando)
SELECT 
  id,
  status_code,
  error_msg,
  created
FROM net._http_response
ORDER BY created DESC
LIMIT 10;

-- 4. Verificação de integridade contra duplicidades recentes
SELECT 
  data,
  valor,
  descricao,
  workspace_id,
  count(*) AS ocorrencias
FROM public.transacoes
WHERE created_at > now() - interval '24 hours'
GROUP BY data, valor, descricao, workspace_id
HAVING count(*) > 1;
```

### 7. RESOLUÇÃO DEFINITIVA DE AUTENTICAÇÃO E STATUS DA SERVICE ROLE KEY

A pendência de autenticação do despachante cron foi **definitivamente resolvida em produção**:
* Foi identificado que o gateway Kong exige cabeçalho de gateway válido (`apikey: anon_key`), enquanto o Deno runtime das Edge Functions valida chamadores de serviço/cron comparando `Authorization: Bearer <token>` e `x-cron-secret` em tempo constante (`timingSafeEqual`) contra `CRON_SECRET`.
* Um `CRON_SECRET` de alta entropia (256 bits) foi gerado e registrado nos Secrets do Supabase e no Supabase Vault (`vault.decrypted_secrets`), com `anon_key` também cadastrada no Vault.
* A função `public.cron_dispatch_edge_function()` foi atualizada com headers completos (`apikey`, `Authorization`, `x-cron-secret`) e timeout estendido para 120s.
* A execução agendada de `eyemobile-sync-every-30m` às 22:30:00 UTC comprovou autenticação perfeita com HTTP 200 e reconciliação concluída com sucesso.

#### Estado Atual das Credenciais Legadas (`anon` e `service_role`):
1. **Despachante SQL (`cron_dispatch_edge_function`):** Migrado com sucesso no Vault para `sb_publishable_` (no header `apikey`) e `CRON_SECRET` (no header `Authorization`). Não utiliza mais nenhuma chave legada.
2. **Frontend SPA (Vite):** Configurado com `VITE_SUPABASE_ANON_KEY=sb_publishable_...` e testado com build de produção validado. Zero dependência de chaves legadas.
3. **Edge Functions (Deno):** Operam internamente com a chave moderna `sb_secret_p9IlF...` injetada pelo Supabase.
4. **Supabase Vault:** `anon_key` atualizada para 46 caracteres (`sb_publishable_9H7Zu...`). A chave `service_role_key` legada permanece no Vault unicamente como salvaguarda passiva.
